# 05. Reflexión Técnica Final

**Pregunta guía:** *¿Qué prueba habría evitado mi error más costoso?*

El error más costoso detectado durante la integración fue la incidencia crítica **INC-002**, donde la aplicación fallaba al intentar deserializar documentos de Cloud Firestore que carecían del campo opcional `descripcion` o contenían valores nulos (`type 'Null' is not a subtype of type 'String'`). Este fallo habría podido evitarse desde el primer día mediante una **prueba unitaria de casos borde (edge cases) sobre el método `Tarea.fromMap`**, validando mapas incompletos, nulos y con tipos inesperados antes de conectar la interfaz de usuario con la base de datos real. Al trabajar con bases de datos NoSQL como Firestore, cuyo esquema es flexible, asumir que todos los documentos tendrán siempre la misma estructura rígida es un riesgo alto en producción. Implementar pruebas unitarias del modelo junto con pruebas de widget apoyadas en un `FakeTareasRepository` nos permitió aislar la lógica de datos de la red y verificar estados vacíos y validaciones en milisegundos. Además, el uso disciplinado de `flutter analyze` resultó clave para prevenir errores silenciosos del ciclo de vida asíncrono como el uso de `BuildContext` tras un `await` (INC-003). En conclusión, combinar análisis estático, pruebas unitarias sobre modelos y pruebas de widget reduce drásticamente el tiempo de depuración manual en el emulador.
